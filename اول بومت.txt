اقرأ ملف `docs/SPEC.md` بالكامل قبل تعديل أي كود.

اعتبر `docs/SPEC.md` هو المصدر الوحيد والرسمي للحقيقة (Single Source of Truth) للمشروع.

قبل البدء، اقرأ أيضًا — إذا كانت موجودة:
- `docs/ARCHITECTURE.md`
- `docs/DEVELOPMENT_STATUS.md`
- `docs/DECISIONS.md`
- `docs/AI_HANDOFF.md`
- `package.json`
- مجلد `src/`

افهم حالة المشروع الحالية بالكامل قبل إجراء أي تعديل.

ممنوع إعادة بناء المشروع من الصفر.
ممنوع حذف أو إعادة كتابة Feature موجودة وتعمل لمجرد تغيير أسلوب التنفيذ.
أكمل من آخر حالة وصل إليها المشروع.

نفّذ المهمة الحالية المحددة في:
`docs/DEVELOPMENT_STATUS.md`

التزم حرفيًا بالمعمارية والمتطلبات والقرارات الموجودة في `docs/SPEC.md`، وخصوصًا:

- React + TypeScript + Vite + Tailwind CSS
- Zustand فقط لإدارة الحالة العامة
- Service Layer وفصل الـ UI عن الـ Mock Services
- عدم استدعاء Services مباشرة من Components
- Mock Services فقط في هذه المرحلة
- لا Electron
- لا Backend
- لا SQLite
- لا yt-dlp فعلي
- لا FFmpeg فعلي
- لا Real Downloads
- لا Authentication / Login / Register / Account
- الحفاظ على Electron-readiness للمرحلة المستقبلية
- الالتزام بالـ State Machine المحددة في المواصفات
- الالتزام بـ RTL/LTR وArabic/English
- الالتزام بـ Light/Dark/System
- الالتزام بالـ Accessibility
- الالتزام بالـ Tests المطلوبة
- الالتزام بالـ Documentation وAI Handoff

ممنوع اتخاذ قرار معماري جديد من نفسك إذا كان القرار يؤثر على:
- Architecture
- Zustand
- Service Layer
- Data Model
- State Machine
- Persistence
- Electron Readiness
- فصل UI عن Business Logic

إذا ظهرت مشكلة تتطلب تغيير قرار معماري محسوم:
1. اشرح المشكلة بوضوح.
2. اشرح البدائل الممكنة.
3. وضّح تأثير كل بديل على المشروع.
4. توقف وانتظر موافقتي.
5. لا تنفذ التغيير قبل موافقتي.

أما القرارات التقنية الصغيرة والقابلة للعكس، فيمكنك اختيار الحل الاحترافي المناسب لها وتسجيل القرار في:
`docs/DECISIONS.md`

ممنوع تنفيذ أي أمر Git نهائيًا.

لا تستخدم:
- git add
- git commit
- git push
- git pull
- git checkout
- git switch
- git merge
- git rebase
- أو أي أمر آخر يبدأ بـ `git`

أنا المسؤول الوحيد عن Git والـ commits والـ branches.

أثناء التنفيذ:
- لا تترك TODO في الأجزاء الأساسية.
- لا تستخدم `any` إلا عند الضرورة القصوى مع تعليق يشرح السبب.
- لا تضف مكتبات جديدة لمجرد أنها Best Practice أو Trend.
- لا تغيّر المكتبات أو الـ Stack الأساسي بدون سبب تقني واضح وموافقة عند الحاجة.
- لا تستخدم `dangerouslySetInnerHTML`.
- لا تنفذ Shell Commands.
- لا تضف أي تكامل حقيقي مع Windows أو Electron في هذه المرحلة.

بعد الانتهاء من الـ Feature الحالية:

1. شغّل الاختبارات.
2. أصلح أي أخطاء ناتجة عنها.
3. شغّل:
   `npm run build`
4. تأكد أن الـ Build ناجح.
5. حدّث:
   - `docs/DEVELOPMENT_STATUS.md`
   - `docs/CHANGELOG.md`
   - `docs/AI_HANDOFF.md`
6. حدّث `docs/KNOWN_ISSUES.md` إذا ظهرت مشكلة جديدة.
7. حدّث `docs/DECISIONS.md` إذا تم اتخاذ قرار تقني مهم.
8. اترك المشروع في Stable Checkpoint:
   - الكود يعمل
   - الاختبارات ناجحة
   - Build ناجح
   - Documentation محدثة
9. لا تنفذ أي Git Commit.

في نهاية العمل، أعطني تقريرًا مختصرًا يحتوي على:

- ما الذي تم تنفيذه.
- الملفات الرئيسية التي تم تعديلها.
- الاختبارات التي تم تشغيلها ونتيجتها.
- نتيجة `npm run build`.
- أي مشاكل متبقية.
- ما هي المهمة التالية المقترحة حسب `docs/DEVELOPMENT_STATUS.md`.

إذا كانت الـ Feature الحالية مكتملة ومستقرة، أخبرني بوضوح:

"الـ Feature جاهزة للمراجعة والـ Git Commit اليدوي."

ابدأ أولًا بفهم المشروع وقراءة ملفات الـ Documentation، ثم نفّذ المهمة الحالية فقط.
